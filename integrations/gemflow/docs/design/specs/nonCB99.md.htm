插件：用户选一个流程（开发、视频，或从市场装的、自己写的），它按流程的阶段替用户管三样东西——**当前该看什么上下文、流程走到哪一步、每一步留下了什么**——并在输入框上方常驻一行状态、在面板里画出流程看板。流程是一份普通的 GEML 文档：章节是状态，一张表是边，一张表是变量，守卫是 `data` 块，词汇表只多定义一个 meta 键（`geml-flow/v1`）。每个阶段能用哪些工具、同类工具首选哪个、参数默认取什么，在使用中由你的选择记进工具词典；流程作者只在真正要紧的岔口封路（只在某些阶段能跑的命令、要人批准的边）。 ## 1. 出发点 ### 1.1 为什么是这个形态 effortless 的成功模式是：装上就自动工作，眼前天天有一个证明它有用的东西。Gemflow 照这个路子，但管的是**流程**而不是 effort：开发者用 Claude 做一个功能，从写代码、测试、PR、CI 到部署，每一步发生了什么、下一步是什么、这一步该带哪些上下文，插件都替他记着、摆在眼前。 ### 1.2 为什么建在 geml-agent runtime 上 | Gemflow 需要的 | runtime 已有的 | |---|---| | 流程定义 | GEML 状态图：状态、转换、变量 | | 阶段完成的条件 | **目标** - 一份流程文档在 Claude Code、Codex、Grok、Gemini CLI、DeepSeek Harness 上语义相同；v1 只有 Claude Code 有界面，只接 MCP 的宿主通过 MCP + skill 推进与记录（它们看不到的部分见 §8.5）。 - 两个内置流程与用户流程用同一种格式，引擎里没有内置流程的特殊通道。 - 判断"阶段做完了"靠观测到的事实（退出码、文件、git/CI、人的勾选），不靠模型自报。 - 默认不挡路：流程作者只在要紧的岔口封路；工具的权限与偏好由你在使用中决定（§5.3）。 - 词汇最少：能用 GEML 核心构件（章节、`table`、`data`、`diagram`、`embed`）表达的，不另造词；词汇表只定义一个 meta 键、两个约定的 id 和两张表的列。 **不做（v1）** - 以分支为单位的流程（开发流程）里，直接提交到 `main` 的工作不记 journal。 - 用户在自己终端里跑的命令不触发命令信号；git、文件信号会在会话开始时补齐它们的结果。 - 信号只产生布尔值。 - Codex、Gemini CLI、Grok 的界面（它们的插件接口画不了或要用户手配，见 §10）。 - 插件不替用户切换分支。 ## 3. 总体架构 ``` `match`；`manual`：人在看板上或用 `gemflow mark` 勾选；`committed`、`pr-open`、`pr-merged`、`ci-success`：git 与 CI 的事实（§5.2）。`on` 不为空的变量模型写不了，默认值必须是 `false`。 - `match`：`command` 行是正则，`file` 行是 glob；`ci-success` 行可选，按名字筛 CI workflow。 - `only-in`：只用于 `command` 行，写成 `#状态` 的列表：匹配的命令只能在这些状态里运行（§5.3）。 - `note`：由模型写的变量是给模型的说明（这个变量写什么）；`manual` 行是看板上勾选框的文字。 **`#transitions`**：列 `from`、`to`（必需），`requires`、`approval`、`resets`、`note`（可选）。 - `from`、`to`：`#状态`。一条边称作 `起点→终点`（如 `build→review`），同一对状态之间只有一条。 - `requires`：空，或 `#id` 指向一个守卫。 - `approval`：空或 `yes`。 - `resets`：空格分隔的变量名：走这条边时，这些变量在同一个修订里回到默认值，守卫读的是走之前的值。返工的边用它清掉上一轮的证据。 - `note`：交给模型的这条边的说明。 **边怎么走**： - 有守卫、不要批准的边，在任何一次改动（信号写入、模型的动作、人的推进、证据作废、回滚、进入起点）之后守卫成立就自动走；一个状态至多一条这样的出边。 - 没有守卫的边由模型（`move`）或人走。 - `approval = yes` 的边只由人走（看板上点，或 `gemflow advance`），写了守卫就必须成立，从不自动走。 **流程图**：图里的边与边表按 `起点→终点` 对照；状态直接用状态 id，Mermaid 认不了的 id（比如带 `-` 的）用 `state "wait-human" as waitHuman` 起别名；`[*] -->` 指向起点，`--> [*]` 从终点出发。标签是约定、不检查：有守卫的边写守卫 id，要批准的写 `approval`，其余写一句话；标签里不写 `#`（Mermaid 会当成实体编码的开头）。只读 `A --> B`（可带 ` : 标签`）、`[*] --> A`、`A --> [*]`、`state "名字" as 别名` 这几种行，其余行忽略。 ### 4.3 静态检查 | id | 级别 | 条件 | 5.1 推进 | 谁 | 怎么发生 | `by` | |---|---|---| | 模型 | `move` 走一条出边：守卫写了就必须成立；要批准的边不行 | `model` | | 人 | 在看板上点一条边，或在自己终端运行 `gemflow advance `；这本身就是批准 | `human` | | 自动 | 一次改动之后，当前状态那条有守卫、不要批准的出边守卫成立，立即走 | 记那次改动的来源：信号写入后 `signal`（带 `signal=<变量>`），模型动作后 `model`，人推进后 `human` | 一次写入了几个信号时，自动走的边记在它的守卫所读变量对应的那个信号名下（守卫的 `properties` 或 `required` 里出现的第一个），没有则记最后写入的信号。 一次改动之后连着自动走，走到某个本次已经进入过的状态（出发时所在的状态也算），就停在它前面；自动走的自环因此永远不会被走。 一次转换（模型的 `move`、人的推进）之后的第一条自动边，不会把流程直接带回这次转换刚离开的状态：人把流程从评审退回构建（dev 流程的 `review→build`）时，「构建 → 评审」的守卫即使仍成立，流程也停在构建，不会被立刻弹回去。只有刚离开的那个状态被挡，也只在这一次改动里挡：之后的下一次改动（例如测试重新跑绿）照常走这条边，一条链隔一步再回到那个状态也照常走。回滚不算这样的转换，它恢复出的状态上成立的自动边照常走。 守卫对三种来源一视同仁。 ### 5.2 变量与信号 | `on` | 何时读 | 值 | |---|---|---| | 空 | 模型调用
