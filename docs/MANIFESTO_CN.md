# Doc-as-a-Base 立场书

> 文档需要的不再只是一个格式，而是一个接口。

## 立论

一份技术文档现在有两个读者。第一个读完就走，第二个读完会动手改。

为第二个读者，我们主张一种新的文档形态，并给它起了名字：

> **Doc-as-a-Base**：物理上仍是人类可读的纯文本，操作上却暴露数据库式接口的文档。
> 每个结构块有主键，块之间的引用是外键，嵌入是取值而非复制，
> 改写是对单个块的操作而不是对整篇的覆盖。

注意措辞是「暴露数据库式**接口**」，不是「文档就是数据库」。这个区别不是谦虚，是精确——文末「边界」一节会把它说死。

为什么值得为此立一份文书？因为不这样做的代价已经是日常：你让 agent 改第 3 节的一个参数，它改对了——同一次提交里，第 7 页表格里的一个数字被「顺手对齐」了，三周后才被发现。这不是模型不够聪明，是**在一个没有接口的地方做写操作**的必然结果：为了定位一处，必须读入一片；读入了，就有能力改坏。

## 四大定律

任何声称解决这个问题的格式，必须同时满足四条。它们不是四个可选特性，是同一个根长出来的四根枝：**不能寻址就无法安全写入，不能投射就只能复制，不能校验就拦不住坏写入，不能回滚就无法从坏写入里恢复。**

### 第一定律 · 寻址 (Addressability)

**每个结构块必须有稳定的、机器可识别的主键，脱离上下文也能被单独读取和替换。**

判据很硬：`read(id)` 只返回那一块，`write(id)` 只替换那一块——其余部分不但不该被改，而且**根本不该被加载**。没被加载的东西不可能被改坏。这是隔离，不是自律。

### 第二定律 · 投射 (Projection)

**引用必须是取值，不是指路。**

链接告诉你真相在哪，副本给你一份过期的真相；投射给你真相**此刻的样子**。判据：嵌入一个块之后，源头一改，所有嵌入处跟着变；不存在需要人工同步的第二份。复制粘贴造出来的每一份副本，从诞生那一刻就在漂移——投射存在的意义就是让「同步副本」这项工作消失。

### 第三定律 · 校验 (Verifiability)

**块之间的引用是外键，必须在构建期校验。引用不解析 = 构建失败 = 非零退出。**

对人的意义是文档不会烂成死链。对 agent 工作流的意义更直接：**写入路径上多了一道门**。坏的生成写不进去，不需要等人 review 才发现。

### 第四定律 · 可逆 (Reversibility)

**出错时必须能只回滚出错的那一块，不牵动文件其余部分。**

这条最容易被误读成「重新造 Git」，恰恰相反。Git 的粒度是文件与提交。当 agent 写坏了一个块、而人同时在同一文件的别处做了修改，文件级回滚会把人的工作一起丢掉。**这个粒度 Git 在结构上给不了**——不是它做得不好，是它不在这一层工作。

## 它站在哪里：没有替代谁

四条定律**不是用来给现有格式打分的**。每种格式都是为一个具体问题生的，而且大多把那个问题解决得很好——它们只是从来没被要求解决「机器反复改写」这一个问题。

| | 它为什么而生 | 面对「机器反复改写」时 |
|---|---|---|
| Word / Notion | 人的即时编辑与协作 | 不进 CI，不在这个问题的讨论范围内 |
| **Markdown** | 人写人读、到处能渲染——而且做得极好 | 缺的不是语法，是**可供程序抓取的边界** |
| JSON / XML | 数据序列化与交换 | 机器完美，但人写不了长文 |
| AsciiDoc / Typst | 严谨排版与出版 | 有 label 有 include，但工具链是排版器，不做 get / set，断链不当构建错误 |

所以正确的说法是**多了一层**，不是换掉一个。Doc-as-a-Base 做源，Markdown 做交付物：`geml doc.geml --to md`。这个投影是**有损**的——块 id 和绑表的图表回不来，目标格式没有语法位放它们，工具会逐条报给你。认掉这个损耗比假装无缝更可信。

## 参考实现

[GEML](https://github.com/geml-spec/geml) 是按这四条做的一个实现，四条定律对应四组可以立刻验证的动作：

```console
$ geml get  spec/GEML-spec.geml '#abstract'   # 寻址：只取这一块
$ geml check bad.geml                          # 校验：引用断了就非零退出
error: unresolved reference `#nope` (line 3)
$ geml revert doc.geml '#api-auth'             # 可逆：只退这一块
```

投射是一个块类型：

```
=== embed {src=spec/GEML-spec.geml#abstract}
===
```

渲染时就地呈现目标块的此刻状态；目标缺失，`geml check` 让构建当场变红。

可复现的一个数：`spec/GEML-spec.geml` 全文约 5.6 万字节，`geml get '#abstract'` 返回约 590 字节——**约 95 倍**之差。重点不在这个数字，在**块恒定**：比值就是「整篇除以一块」，它随文档变大而变大——你要改的东西越大，agent 不必读的部分就越多。规范本身就是用 GEML 写的，clone 下来自己验。

给 agent 的接入是一行：

```console
$ claude mcp add geml -- npx -y @geml/geml@latest mcp --root /abs/path/to/docs
```

工具与 CLI 动词同名（`geml set` → `geml_set`）；每次写入先解析再落盘，会破坏文档的写入带着诊断被拒绝，且写前自动存一条块级历史。

## 边界

一次说完，不重复。

**它不是数据库。** 查询是 O(N) 的字符流遍历，没有索引；并发写至多整文件锁；没有跨文件事务。借的是数据库的**操作语义**——按主键定位、校验引用、取值投射、回滚单行——不是它的运行时属性。拿它去扛高并发读写是找死。

**生态是全新的。** GitHub 不原生渲染 `.geml`；把已有 Markdown 转进来是有损的；模型对它的初始熟悉度不如 Markdown；目前只有一个实现——第二个独立实现是公开征集中的事项。

**校验拦不住内容写得烂。** 它拦的是结构破坏和断引用。agent 把一段话写得很蠢，它一个字都不会说。

## 这套要求适用于谁

如果你在让 agent 长期维护一份会不断增长的技术文档、规范、runbook 或知识库，并且已经被「改对了一处、顺手改坏了另一处」咬过——四条定律就是你缺的东西，**不管你最后是用 GEML，还是自己造一个满足这四条的东西**。

如果你没被咬过，Markdown 挺好。

而如果你读到这里想的是「这四条我能实现得更好」——那正是我们最想见到的读者：conformance suite 是公开的，第二个独立实现是这份规范此刻最缺的东西。入口在 README 的「状态与贡献」。
