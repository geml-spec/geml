# Doc-as-a-Base（文档即真相之源）宣言

*[English](https://github.com/geml-spec/geml/blob/main/docs/MANIFESTO.md) | 中文*

> 文档需要的不再只是一个格式，而是一组动词。

你让 agent 改文档里的一节。它改对了，也顺手改坏了另一节——而同一个文件里，你自己刚写了两小时。想退回去，`git checkout` 会把两边一起卷走。

不是 agent 的错，也不是 Git 的错。是这份文档里根本没有「一块」这个东西：它是一整条字符流，所以最小的读写单位是整个文件，最小的回滚单位也是。

而 AI 工程化正让文档以前所未有的速度增殖、碎片化——这一幕不是偶发，是从此每天都会发生。

一份文档现在有两个读者：第一个读完就走，第二个读完会动手改。第二个读者要的不是更好的排版，是一组动词。

## 我们命名它

为这个读者，我们宣告一种新的架构风格：

**Doc-as-a-Base（文档即真相之源）**。

[REST](https://www.ics.uci.edu/~fielding/pubs/dissertation/top.htm) 给散落的资源统一了两样东西：名字（URI），和一组共同的动词（GET / PUT / POST / DELETE）。Doc-as-a-Base 对文档的每一块做同一件事——名字是 `#id`，动词是 get / set / add / delete。

Base，读作 **base of truth**：

> **Doc-as-a-Base（文档即真相之源）**：一份仍是纯文本、但自带动词的文档——
> 每块有名字，可以单独取；引用受核验，断了构建就红；
> 嵌入是取值，不是复制；回滚只退一块，不推倒整篇。
> 它是所有交付物的**基座（base）**：`.md`、`.html` 都是从它投影出去的视图。

## 我们更看重

在新范式里，我们主张：

**按块寻址** 高于 整篇读写  
**引用取值** 高于 复制粘贴  
**构建期报错** 高于 静默腐烂  
**单块回滚** 高于 整篇重来

四条缺一不可：不能寻址就无法安全写入，不能投射就只能复制，不能校验就拦不住坏写入，不能回滚就无法恢复。

旧范式的事物并非没有价值——其中一些，我们至今每天在用——但为了与机器读者共写，我们更看重左边。

这四组取舍，不是用来给现有格式打分的。每种格式都为一个具体问题而生，而且大多把那个问题解决得很好。它们只是从来没被要求解决「机器反复改写」这一个问题——Markdown 诞生的 2004 年，还没有人需要一份能被程序原子化改写的文档。

## Doc-as-a-Base 四大定律

主张要能验，才不是口号。上面四条，每条都配一个可判定的判据——面向第二个读者的格式，四条必须同时满足。

### 第一定律 · 寻址（Addressability）

**每个结构块必须有稳定的、机器可识别的主键，脱离上下文即可被单独读取与替换。**

判据：`read(id)` 只返回那一块，`write(id)` 只替换那一块——其余部分不但不改，根本不加载。

没被加载的东西不可能被改坏——要隔离，不要自律。

### 第二定律 · 投射（Projection）

**引用必须是取值，不是指路。**

判据：嵌入之后，源头一改，所有嵌入处跟着变；不存在需要人工同步的第二份。

副本自诞生就在漂移；投射让「同步副本」这项劳动消失。

### 第三定律 · 校验（Verifiability）

**块间引用必须在构建期受核验。**

判据：引用不解析，构建失败，非零退出。

写入路径上多出一道门：坏写入挡在落盘之前，不等 review。

### 第四定律 · 可逆（Reversibility）

**出错时必须能只回滚出错的那一块。**

判据：回滚只触及那一块，文件其余部分逐字节不动。

开头那一幕，根因就在这里：Git 以文件与提交为单位，结构上给不出块级粒度。不是 Git 不好，是它不在这一层。

寻址、投射、校验、可逆——四样能力，在各自的领域都有成熟方案：数据库有主键，XML 有 XInclude，Schema 能校验，Git 管历史。不寻常的不是其中任何一样，是把四样同时装进一种人类可读的纯文本。（逐格式的对照，见[能力矩阵](https://github.com/geml-spec/geml/blob/main/docs/comparisons/COMPARISON_CN.md)。）

## 参考实现

[GEML](https://github.com/geml-spec/geml) 是按这四条做的一个实现，四条定律对应四组可以立刻验证的动作：

```console
$ geml get  spec/in_geml_format/GEML-spec.geml '#abstract'   # 寻址：只取这一块
$ geml check bad.geml                          # 校验：引用断了就非零退出
error: unresolved reference `#nope` (line 3)
$ geml revert doc.geml '#api-auth'             # 可逆：只退这一块
```

投射是一个块类型：

```
=== embed {src=spec/in_geml_format/GEML-spec.geml#abstract}
===
```

渲染时就地呈现目标块的此刻状态；目标缺失，`geml check` 让构建当场变红。

可复现的一个数：`spec/in_geml_format/GEML-spec.geml` 全文约 7 万字节，`geml get '#abstract'` 返回 591 字节——**约 119 倍**。写下这句时是 119 倍；你 clone 下来大概率更高，因为规范一直在长，而那一块没有。这正是重点：比值就是「整篇除以一块」，文档越大，agent 不必读的部分越多。规范本身就是 GEML 写的，自己验。

给 agent 的接入是一行：

```console
$ claude mcp add geml -- npx -y @geml/geml@latest mcp --root /abs/path/to/docs
```

工具与 CLI 动词同名（`geml set` → `geml_set`）；每次写入先解析再落盘，会破坏文档的写入带着诊断被拒绝，且写前自动存一条块级历史。

## 边界

一次说完，不重复。

**它不是数据库。** 查询是 O(N) 的字符流遍历，没有索引；并发写至多整文件锁；没有跨文件事务。借的是数据库的**操作语义**——按主键定位、校验引用、取值投射、回滚单块——不是它的运行时属性。拿它去扛高并发读写，是用错了层。

**生态是全新的。** GitHub 不原生渲染 `.geml`；把已有 Markdown 转进来是有损的；模型对它的初始熟悉度不如 Markdown；目前只有一个实现——第二个独立实现是公开征集中的事项。

**校验拦不住内容写得烂。** 它拦的是结构破坏和断引用。agent 把一段话写得很蠢，它一个字都不会说。

## 这套要求适用于谁

如果你在让 agent 长期维护一份会不断增长的技术文档、规范、runbook 或知识库，并且已经被「改对了一处、顺手改坏了另一处」咬过——四条定律就是你缺的东西，**不管你最后是用 GEML，还是自己造一个满足这四条的东西**。

如果你没被咬过，Markdown 挺好。

而如果你读到这里想的是「这四条我能实现得更好」——那正是我们最想见到的读者：conformance suite 公开在案，第二个独立实现是这份规范此刻最缺的东西，入口在 README 的[「状态与贡献」](https://github.com/geml-spec/geml/blob/main/README_CN.md#contributing)。

这份宣言不设签名页。以 GEML 格式写出一个文件，就是签名。
