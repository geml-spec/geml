# 为什么大模型时代需要一种全新的文本格式？

每个人都会问这个问题：“我们已经有了 Markdown、AsciiDoc，也有 JSON、XML，为什么还需要发明一种新的格式？”

要回答这个问题，我们需要从一个你可能每天都在经历的痛苦场景说起。

## 场景：当人类与 Agent 共同写作

假设你在某个系统项目撰写或修订一份长篇设计文档或技术报告。由于篇幅长、迭代频繁，你需要反复对部分段落进行取舍、重组或删除，而文档其他地方（或别的文档里）散落着对这些段落的引用与数据嵌入。

*   **如果靠手工修改**：极易遗漏某处链接，导致静默的死链和数据不一致。
*   **如果交给 AI Agent 处理**：改动极其容易超出预期范围，Agent 有时会把整个段落的风格和内容改成你不想要的版本。
*   **如果使用 Git 进行版本管理**：当你不想把每一次不成熟的中间草稿都提交到 Git 上，那么审查和挑选 Agent 修改的内容（并在必要时回滚错误的部分）就会让人变身苦力编辑。

为什么会这么痛苦？因为传统文本格式并没有为这种“人机共写”的场景设计。

## “分开”的传统范式正在瓦解

文本是知识生产与工程协作最通用的介质——人用它思考和表达，机器读它、改它、照它行动。

而同一段文本要同时服务这两类读者，它们要的东西天然相反：
*   **机器要精确**，精确靠形式约束和工具校验；
*   **人要好懂**，好懂靠自然的结构和表达。

过去，**“分开”是这对矛盾唯一可行的解**。每种格式只为自己的消费者优化：
*   **人写给人**：Word / Google Docs / Markdown，为阅读舒适优化，让出机器要的精确；
*   **人写给机器**：编程语言 / 协议 / Schema，为精确执行优化，代价是人得先学一门专业；
*   **机器写给人**：为各种终端与介质分别建一条渲染管线；
*   **机器写给机器**：JSON / Protobuf，高效对传，可读性只是顺带。

“分开”行得通，靠的是一个隐含前提：**一份文本只有一类作者、一类主要读者，写的人清楚自己在为谁写。**

然而，**LLM（大语言模型）把这个前提彻底取消了。**

同一份文档，人和 Agent 共读、共写、反复改写——两类读者第一次同时坐在同一份文本的两端。“为单一消费者优化”失去了意义。这就是标题中“现在”的含义：**不是文本变了，是读者变了。**

## 读者改变带来的两场危机

读者变了之后，旧的工作方式在两头同时垮掉。

### 危机一：撑网的人不在了

任何工程交付物都只是某一刻的版本快照，快照背后是海量中间产物：需求草稿、数据、结构实验、评审意见、废弃方案、一次次的 diff。这些碎片散落在上文提到的各种模式的格式里。

过去，这张碎片网靠**人**撑住。要驱动机器得先懂机器，要说服人得先懂读者，这种被迫的理解加上相对低频的变更，让一个人或一小群人勉强记得住哪个碎片是权威的、哪条引用还有效。

但 AI 把驱动机器的门槛降到了零——人不再需要懂机器，全局的心智地图随之失去来源。而模型输出本身带有随机性。当“不理解”叠加“不可复现”，工程过程就从白盒变成了黑盒。

### 危机二：碎片爆炸与真相源（Source of Truth）丢失

所谓 AI 工程化（上下文工程、评测、护栏、Agent 工作流重放等），本质都是在校准这个黑盒。然而，**校准本身就在制造副本**。

每一次校准都往上下文里堆东西：同一个事实被摘要一次、重述一次、局部修改一次、贴进 prompt 一次。链条断在没人看见的地方——架构图引用了表格里的数字，章节引用了另一节的结论，Agent 动了文档结构，人类改了其中几句——没人知道依赖何时断裂。

副本造出来就是漂移的起点。真相源（Single Source of Truth）被复制、被转换、散落成各处残片，不再唯一。副本越积越多，超出模型一轮吃得下的上下文窗口，只好拆得更碎、再堆一层——碎片化自己滚成雪球。

## 解法：让碎片引用真相，而不是复制真相

解法方向因此清晰：**让碎片引用真相，而不是复制真相。**

每个碎片必须知道自己的源头在哪，需要时从源头**取值（Transclusion）**——取来的切片小而短命，过期就重取，不留长命副本。更重要的是，碎片之间的依赖网络本身必须可被机器持有、**被机器强校验**。只有状态确定了，可预测、可复现，工程化的演化闭环才能重新闭合。

为了做到这件事，承载文本的格式必须在语法层面给出四样核心能力：
1. **块级寻址（Block-level Addressing）**
2. **引用式投射（Transclusion / Embeds）**
3. **构建期校验（Build-time Validation）**
4. **块级回退（Block-level Reversion）**

### 为什么现有格式给不全？

并非没有前人尝试过。Markdown / HTML 有链接，Wiki 有双链，Obsidian 有 `![[…]]` 嵌入，AsciiDoc 有 `include`。

但它们都有硬伤：
*   要么**只是导航链接**：那头的内容悄悄变了或删了，你这边无从感知。
*   要么**嵌入没有校验**：源头没了，页面上安静地指向空气（静默 404）。
*   **粒度太粗**：寻址往往只能到整个文档或标题级别，无法精确到段落、表格或图表。
*   最致命的是，没有任何一种主流人类可读格式把“断链”当成**构建错误（Build Error）**。

引用要成为**取值**而不是**指路**，缺的正是那道门：源头一改，处处跟着变；源头没了，构建当场就红。

### 为什么必须写进语法，而不是做成外部工具？

活在 Linter 里的约定只是建议，随时会被绕过；而写进语法的约束是每个解析器实现都必须履行的契约。只有把块 `#id`、嵌入和引用校验门直接写进规范，任何人凭这份规范写出的解析器，才会一致地拒绝坏引用。这也是**格式**与**产品**的本质分别。

### 大上下文、上下文工程、缓存和记忆，解决不了碎片化与漂移吗？

解决不了，因为它们优化的是另一侧。**大上下文让副本读得下，上下文工程让副本挑得准，缓存让副本变便宜，记忆让副本跨会话——整个栈都在优化副本，但没有一层碰过原本：谁是权威、怎么指到一块、写坏了怎么拦、拦不住怎么退。**副本技术越繁荣，越需要一个有地址、有指纹、有校验的原本让它们对齐——不然优化的只是“更快地读到过时的东西”。上下文早已百万级，前沿 harness 却全体拒绝整文件重写——old_string/new_string、search/replace 全是各家私造、互不兼容的“按块改”，寻址早该下沉为公共一层。

## GEML 是如何设计的

GEML 并没有试图让任何人放弃原有格式（比如写博客依然可以用 Markdown），它是给现有生态补上这张缺失的网络，为长生命周期的工程文档、规范和 Agent 知识库提供基座。

这四大能力，对应 GEML 纯文本设计里的四大支柱：

### ① 统一类型块 + 原生 `#id`（寻址）
在 GEML 中，全语言只有一种块语法：
```geml
=== type {#id .class key=val}
content
===
```
代码、表格、图形、公式、提示框、元数据，统统是它。每块强制（或按需）分配一个全局唯一的 `#id`，它是**块级引用把手，而不是文档级导航链接**。改一块不用动全文；喂给模型（LLM）的也只是这一块——切片要多小有多小，过期随时从源头重取。

### ② 块级嵌入（投射）
你可以使用 `=== embed {src=doc.geml#id}` 语法。引用即取值：渲染时嵌入的是那一块的**此刻状态**，不是一份手工拷贝。最终的交付物由此成为块粒度的组装——从各处取恰好需要的那几块拼成，而不是把整篇搬过来。

### ③ 构建期校验 `geml check`（校验）
解析不到的引用属于**构建错误**，不是渲染时才暴露的静默 404。
无论是图表与表格的绑定、跨文档的引用，还是嵌入目标，全过同一道门。一旦发生断链，`geml check` 会让构建当场卡住。绝不允许错误进入下一环。

### ④ 伴生历史 `.gemlhistory`（回退）
这是一种独立于 Git 的回退机制。纯文本伴生文件会在本地静默记住每一块的演进，使用 `geml revert` 可以**只回退出错的那一块**。
当 Agent 擅自写坏了一块，而你同时在同一文件的别处做了修改时，如果是 Git 文件级回滚，会把你的工作一起丢掉。**这种单块粒度的安全回滚，Git 在结构上给不了，GEML 在这里补上了。** 它是离线可用的，Agent 也能顺着它读懂文档是如何演变到今天的。

## 结语

回到刚才撰写长文的场景。有了 GEML，每个段落和类型块都有独立的 `#id`，你可以约束 Agent 只修改特定块，防止改动蔓延；如果有章节删改导致引用断裂，`geml check` 会让构建当场失败，绝对不会漏掉任何一条死链；而 `.gemlhistory` 在本地自动记录每块的微观演进，无需频繁提交 Git 也能随时单块精准回退。

文本的本质没有变，但我们书写、使用文本的协作网络，是时候升级了。
