GEML 调研图解 · awesome-markdown 清单 · 2026-09-30

Markdown 变体版图

mundimark/awesome-markdown 收录了一批想修补或取代 Markdown 的项目，GEML 自己也在它的「Beyond Markdown」一节里。这一页逐个看它们做了什么，和 GEML 在哪里撞车，在哪里走的是另一条路。清单外有几个项目离 GEML 更近，也一并放进来，单独标出。

看板 通用块 id 与引用检查 查询与改写 嵌入与同步 组件与扩展点 面向 agent 修订标记 启示 依据

结论。没有哪个项目同时做了 GEML 的三件事：一种带类型的块，每块有可寻址的 id，引用在构建时和每次写入前都被检查，出错就拦下。

单看其中一件，都有人做得比 GEML 早或比 GEML 深。通用块和属性是 Djot、Pandoc、MyST、Markdoc 的共识；带规则 id 的校验，Markdoc、mystmd、Carve 都有；按选择器查询和改写 Markdown，mq 做得比 geml get 更像一门语言。GEML 的不同在于把这三件事绑在一起，再加上按块写入的命令行、MCP 和块级历史。

功能上最接近的是 Carve，但它的影响力还很小。它和 GEML 在清单的同一节，今年 5 月才创建，已经有 lint、JSON AST、补丁式编辑、MCP 服务和 agent skill，推进得很快；但只有 32 个 star，也没有找到外部用户。结合影响力看，它是值得跟踪的项目，眼下不是主要对手。它和 GEML 的差别在三点：地址是标题 id 和 AST 路径，写入交给补丁确认，不兼容 Markdown。

通用块

大家都走到了「一种通用块加属性」

Markdown 的块是一个个特例：代码、引用、列表、表格各有各的规则。后来者几乎都收敛到同一个办法：一种通用容器，用属性区分用途。区别在于类型集合是开放还是封闭、id 有没有规则、块里的正文怎么解析。

引用

id 大家都有，把坏引用当错误的很少

几乎每个变体都能给块起 id、链接过去。分歧在于：链接指向一个不存在的 id 时，工具说什么。

查询

查询与改写：按选择器，还是按 id

不写整篇、只取或只改一部分，是 GEML 命令行的核心。清单里有两个工具在做相邻的事：mq 用类似 jq 的语法查询和改写 Markdown，darnlink 用 UUID 锚住链接，文件挪走了也能修回来。

嵌入

嵌入与同步：拉进来，还是推回去

把别处的内容放进文档，是最常见的扩展需求。清单里 mdcode、Slidev、markedpp、MultiMarkdown 各有一种写法，清单外的 AsciiDoc 也有。分歧有两处：引用的是行号还是名字，找不到时报不报错。

扩展

组件和扩展点：代码进文档，还是词汇进文档

想在 Markdown 里放一张图表、一个表单、一段交互，有两条路。一条是让文档直接写组件代码，另一条是让文档只写声明，由渲染器按一份词汇表去解释。

agent

面向 agent：2026 年大家都做了 MCP

「让 agent 只读写一部分，不整篇重写」在今年成了共识。Slidev 在 7 月加了 MCP，Carve 的 MCP 是 9 月建的，mq 和 demarkus 也各有一个。差别在三个地方：地址稳不稳，写之前查不查，改坏了能不能退回去。

修订

改动记在正文里，还是记在旁边

CriticMarkup 是清单「语法扩展」一节里唯一和修订有关的项目。

启示

对 GEML 意味着什么

四件事：什么是真正独有的，谁是要正视的对手，哪些东西值得借，哪些不必担心。

独有 三件事绑在一起

带类型的块、作者写下的稳定 id、写入前整份检查，这三件事单拿出来都有人做过，放在一起的只有 GEML。再加上按块写入的命令行和 MCP、块级历史，以及直接读现有 .md 的能力：Carve 和 Djot 都要求先把文档转换过去，GEML 不用。

最近 Carve：功能近，影响小

同一节、同一套说法：lint、JSON AST、补丁式编辑、MCP、agent skill。它今年 5 月才创建，已有 64 个仓库、2,200 个测试用例、三套实现，9 月底一天几十个提交；但只有 32 个 star，没有找到外部用户。结合影响力看，它是要跟踪的项目，不是眼下的主要对手。它和 GEML 的差别在任意块的稳定地址、写入即检查、兼容现有 Markdown 这三点，讲 GEML 时这三点也该放在语法之前。

影响力 按影响力看

思路相撞的两个都小：Carve 32 个 star，mq 1,040 个。影响大的是 Slidev（48,891）、Pandoc（46,456）、MDX（19,809）和 Markdoc（8,494）。评估对 GEML 的影响时，以后者为准：Slidev 说明按单元读写的 MCP 已经进了主流工具；Markdoc 是讲 GEML 时最好的参照系。

可借鉴 六件 GEML 还没有的事

行内元素的属性和 id（Djot、Carve）；按名字引用源码片段（mdcode、Slidev 的 region，AsciiDoc 的 tag）；把文档里的代码改动推回源文件（mdcode）；文件搬家后修复跨文档引用（darnlink）；待审的修改建议（CriticMarkup）；把内容哈希交给调用方做写前校验（Carve、demarkus）。

不必担心 底座和另一层

CommonMark、GFM、VFMD 是 GEML 散文部分的来源；MultiMarkdown、Markdown Extra 这些老扩展是特例语法的集合，GEML 已经把它们收进一种块里。MDX 是「文档即程序」的另一条路。MarkWay 和 mk-notes 在协议和同步这一层，不在文档格式这一层。

建议
「可借鉴」里的六件事，按项目的规矩都应在设计文档里有名字和阶段。其中两件最小、最贴近现有功能：让 get --json 和 MCP 返回内容哈希，配合选择器里的内容地址做写前校验；按 region 引用源码，补在 code {src=} 上。
