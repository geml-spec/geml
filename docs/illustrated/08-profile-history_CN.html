GEML 图解 · geml-history

.geml 文件只放当前版本；同名的 .gemlhistory 边车放历史：从当前版本往回的反向补丁，加上完整快照。边车自己就是一份 GEML 文档，靠 profile = "geml-history/v1" 放行三个块类型；它自带一份「已提交当前版」的镜像，所以重建任何旧版本都不依赖活文件、不依赖 git、不依赖网络。这一页把 profile 的每条规则和 geml history 四个动词的实测放在一起。

14 条规则，各自的出处和状态

规范已定 profile 文档写死的（它自称 Stable）。实测 文档不规定、工具今天这样做。实现偏差本页未发现。

规范已定 12实测 2
规则出处状态
1应用层 profile，核心一字未改；不认识它的处理器完全合规。存在由边车文件表明，词汇由边车自己的 meta 声明；不许从 .gemlhistory 扩展名或 history-of 键推断（§8.6 规则 2）。§1 · §1.1规范已定
2声明放行三个类型：history-revision（键 id parent author summary hash newline）、history-keyframe（id hash）、history-blob（lang）。放行只给名字，body 仍是 raw，与未声明时同一模型。§1.1规范已定
3doc.geml 是当前版本的唯一真相，热路径；doc.gemlhistory 是自包含的冷路径，永远带一份已提交当前版的 keyframe 镜像，工具维护、不手改，两者靠哈希对账。§2规范已定
4边车丢了，当前文档完好；活文件丢了，任何版本仍可从边车重建。两个方向都不互相依赖。§2规范已定
5头部 meta 键：history-of、geml-version、current、keyframe-interval。keyframe 和 blob 的正文原样嵌整段 GEML，所以围栏必须比载荷里最长的围栏更长。§3 · §3.1规范已定
6块身份：有 #id 用 id；没有就用内容哈希加结构位置派生的键，算法实现定义，簿记只在边车里、绝不写回活文件。不强制任何块带 id。§4规范已定
7反向补丁四种操作：delete、replace … <- blob:、insert <- blob: <anchor>、move；按写的顺序应用；blob: 引用必须解析到同文件里的 history-blob，否则 error。§5规范已定
8重建：取目标版本或更新的最近 keyframe，沿 parent 链反向打补丁到目标，结果哈希必须等于记录的 hash。不依赖活文件。§6规范已定
9回滚线性、破坏性：截掉目标之后的所有版本，current 改为目标；活文件有未提交改动时必须拒绝，除非调用者明确同意（交互确认或 --force）。§7规范已定
10hash 是整份 .geml UTF-8 字节的 SHA-256，前缀 sha256:，含换行风格（newline=lf|crlf）。版本 id 是 <UTC 时间戳>-<hash 前 8 位>，按时间排序；任何不含糊的前缀可作选择器。§8规范已定
11两种轻重：链断、blob 悬空、重建哈希不匹配是损坏 → error；活文件哈希与 current 不同只是未提交 → warning，不得阻止只读操作。§8 · §9规范已定
12工具生成的每个边车必须在 meta 写 profile = "geml-history/v1"；agent 可以读边车，不该手写补丁、blob、id、hash，用工具的 save / get / restore / verify。§9 · §10规范已定
13CLI：save 追加一版（与 tip 相同则 no-op）；get 无参列出全部、带 rev 打印那一版全文；restore <rev> [--force]；verify 重建并重哈希整条链。rev 写法：0 tip、-N 往回 N、或不含糊的 id 前缀。geml history --help实测
14geml revert <file> #id [--rev sel] 是核心动词，用边车把一个块回到过去某版：拼回、复活或删除。项目的 PostToolUse hook 对 spec/ 下的 .geml 自动 save。geml --help实测
