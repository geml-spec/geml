# GEML `get` / `set` 选择符 — 设计文档

状态:**已定稿**,待实现。
基线:`origin/main` @ `498be34` + 本分支的 history 收敛。
前置阅读:`2026-07-24-geml-block-mutation-cli-design.md` —— §1.1(a) 先给地址再说做什么、§1.1(c) id 是主键、§1.1(e) 无状态、§4.0 id 总原则。本文是那份文档在**读侧寻址**上的补完,不修改它的正文。

---

## 1. 出发点:块都能操作,才叫块可寻址

GEML 的立身之本是「每个块都能被单独操作」。但今天有一类块做不到:**没有 `#id` 的围栏块**。

```
=== note
第一段
===

=== note
第二段
===
```

这两个块今天:

- `get` 只能用 `=== note` 一起取到两个,取不到其中一个;
- `set` **完全够不着** —— 它只认 `#id`;
- 列出档里**根本不出现** —— `listIds()` 遍历的是 `doc.ids`。

工具今天的建议是「先给它加个 `#id`」。这条建议有一个它自己回答不了的场景:**文档不是你想改就能改的**。要求先改文档才能操作一个块,等于承认有一类块操作不了 —— 这与「块可寻址」直接冲突。

本文补上这一块,顺带把 `get` 的选择符语义从「三种互不相干的写法」收敛成一条规则,并让 `set` 共用它。

---

## 2. 一条规则:选择符是过滤器

**选择符是对块的过滤表达式**,`{…}` 里是 key。**同一条省略规则用两次**:`#id` 是 `{#id}` 的省略,`@<hex>` 是 `{@<hex>}` 的省略 —— 两个都是 key,只是选择性不同。

| 形式 | 含义 | 匹配数 |
|---|---|---|
| 不给 | 空过滤器 → **列出**(见 §6) | — |
| `#id` / `id` | `{#id}` 的省略;id key | 恒 ≤1(规范 §4:id 文档内唯一) |
| `## 标题` | 抄来的标题行,解析成它的 id | 恒 1 |
| `=== type@<hex>[~n]` | `=== type {@<hex>}` 的省略;类型 + 内容 key(见 §3) | 恒 ≤1 |
| `@<hex>[~n]` | 同上,省掉类型;**列出档不印这种形式**(见 §6.1) | 恒 ≤1 |
| `=== type` | 类型筛 | 0..N |
| `=== type {#id}` | 类型 + id key(冗余但合法) | ≤1 |
| `=== type {k=v}` | 其它 key —— **声明,本轮不实现**(见 §7) | — |

标题恒 1,是因为它总有 id(显式写的,或标题文本的 slug)。

**类型筛不按 id 有无过滤**:`=== note` 匹配全部 note,带 id 的也在内。选择符里没有一个字提到 id,按 id 有无筛选会是一条藏起来的规则。

**这条语法由 `get` 和 `set` 共用**,不是便利,是 §4 那条往返不变式逼出来的。

## 3. `@<hex>` —— 匿名块的内容地址

### 3.1 为什么不是序号

最直觉的做法是下标:`=== note[2]`。**否掉了,四条理由,第一条是实测的。**

1. **`#2` 本来就是合法 id。** 规范 §4 对 id 的唯一约束是「文档内唯一」,没有字符文法;`attrs.ts:51` 是 `out.id = tok.slice(1)`,`#` 后面写什么都收。实测 `=== note {#2}` 解析干净、`check` 无诊断、`get` 列出 `#2`。所以 `{#2}` 是不是序号,**取决于文档里有没有人恰好把某个块命名成 `2`** —— 含义看数据脸色,不看你打了什么。（换个记号如 `[2]` 能绕开碰撞,但绕不开下面三条。）
2. **下标不自足。** `{#id}` 本身就是完整地址,所以 `#id` 能当它的省略;`{#2}` 离开前面的 `=== note` 什么都不是。它不是 key,是筛完之后的下标。
3. **它偷偷夹带了一个快照。** §1.1(e) 是明写的无状态:每条命令从零重新解析。而「第 2 个」的完整含义是「**你上次列出时**的第 2 个」—— 把「文档当时的样子」塞进了地址,而命令行上没有这个信息。
4. **落到 `set` 上,失败方式是致命的那种。** 上面插一个 note,下标就指向另一个块 —— **静默写错**,没有任何信号。

### 3.2 内容地址

```
=== <type>@<sha256(块文本, LF 归一) 的前 8 位十六进制>[~n]        规范形式(列出档印这个)
@<hex>[~n]                                                   省掉类型,同样接受
```

`~n` 是逐字节相同块之间的并列消歧:文档顺序第一个不带后缀,其后为 `~1`、`~2`……这里用序号是安全的 —— 两个块内容一模一样,选错的后果只是位置不同,不会内容意外。

**过期时的行为是它相对下标的决定性优势**:

| | 地址过期时 |
|---|---|
| 下标 | 静默指向另一个块 → `set` 写错 |
| `@<hex>` | **匹配不上 → 报错**(exit 1) |

地址同时充当前置条件,等于乐观并发控制。「文档不是你能改的」那个场景,往往正是文档由别人在动的场景,静默写错是最坏结果。

### 3.3 边界

- **拼写沿用 `.gemlhistory`。** 那一层面对同一个问题(无 id 单元怎么寻址),定的就是 `#id | @sha8`,重名加 `~n`(`history.ts:158-168`)。同一个想法、同一种拼写。但**取值不保证相等** —— 两层的切分单位不同(history 按 tile 单位含尾随空行,这里按块的 span),不要假设可以互相搬运。
- **类型前缀是校验,不是装饰。** `=== note@<hex>` 里那个 hash 若命中的是个 `code` 块 → **报错**(exit 1),而不是忽略前缀。否则前缀就成了可以静默写错的摆设,也接不住手改过的地址。省掉类型的 `@<hex>` 形式自然没有这道校验。
- **对全部块生效,不只匿名块。** `@<hex>` 按内容寻址,带 id 的块也能被它命中。列出档只给匿名块印 `@` 地址(带 id 的有更短的地址,见 §6.1),但解析不区分。
- **只覆盖围栏块。** 标题总有 id;散文今天本就不可寻址。
- **绝不进入文档。** `@` 地址只活在命令行与列出输出里。`[[#id]]`、`[t](#id)`、`data=#id`、`[^id]` 这些引用仍然只能用 `#id` —— 否则内容一改引用就断。这条是硬约束。

## 4. `--head` / `--body` —— 由 `set` 反定义

不自己定义,用一条**可测的往返不变式**钉死:

```
geml get f X --head | geml set f X --head   → 文档逐字节不变
geml get f X --body | geml set f X --body   → 文档逐字节不变
```

`X` 两边必须是同一套语法 —— 这就是 §2 共用语法的**推导来源**,不是偏好。

由此推出的边界(实测 `set` 现有行为得到):

| 单元 | HEAD | BODY |
|---|---|---|
| 围栏块 | 开围栏行 | 两道围栏**之间**的行,不含围栏 |
| 标题 | 标题行 | 标题行之后到本节边界的全部行,**含首尾空行** |

标题那条含空行必须有测试钉住:`set #sect --body 'under sect\n'` 会把标题行后的空行一并吃掉,说明它替换的 span 含空行 —— `get --body` 不原样吐出来,往返就不成立。

不给 flag = HEAD + BODY 整块。

## 5. 基数规则:两个动词不同,理由是硬的

| 匹配数 | `get` | `set` |
|---|---|---|
| 0 | exit 1,报出找的是什么 | exit 1 |
| 1 | 内容 | 写入 |
| N | **N 份内容**,按文档顺序原样拼接 | **exit 2,地址不唯一** |

`set` 遇 N 必须报错,不是保守,是 §4.0 的 id 总原则决定的:「**凡在命令上点名了目标 id,放进去的内容就取那个 id;set 必点 → 内容归一化成它**」。N 个目标时没有「那个 id」可归一化,这条原则直接失效 —— 多目标 `set` 不是危险,是**无定义**。读 N 个无害;拿一份内容写 N 个块没有意义。

**N 份内容原样拼接,不插分隔符** —— 输出必须是文档里的字节,不能是合成的。同时往 **stderr** 写一行 `3 \`note\` blocks (L1-3 · L5-7 #warn · L9-11)`,让人知道拿到了几段;stdout 保持纯内容,重定向不受污染。

### 5.1 `--head` / `--body` 在各档的作用

§4 定义了 HEAD/BODY 是什么;这张表定义它们**作用在谁身上**:

| | 列出档(不给选择符) | 精确档(`#id`/`## 标题`/`@<hex>`) | 类型筛(`=== type`) |
|---|---|---|---|
| `--head` | **exit 2** | 那一个的头行 | **每个匹配的头行,逐行** |
| `--body` | **exit 2** | 那一个的正文 | **每个匹配的正文,顺序拼接** |
| 两个同给 | **exit 2** | **exit 2** | **exit 2** |
| `--json` 与二者同给 | **exit 2** | **exit 2** | **exit 2** |

类型筛档**逐个作用**而不是失效 —— 一旦承认 `=== note` 是模式匹配,「取每个匹配的头行」就是完全良定义的,而且比报错有用。今天这两个 flag 在多匹配时被静默丢弃。

列出档报错的理由见 §7:那里没有块可细化,这两个 flag 在这一档没有任何合理含义,静默忽略会让 `get f --head` 与 `get f` 输出完全一样 —— 一个打错的命令静默做了另一件事。

### 5.2 `set` 在 `@` 地址上的 id 归一化

`@<hex>` 不是 id,所以「归一化成它」无对象。规则:

- `--body`:不涉及头行,无 id 问题。
- `--head` / 整块:内容**原样使用,不归一化**(与 `add` 同);内容自带的 id 若与文档内其它 id 撞车,由 §4.0 的统一写盘守卫拦下。

这顺带给出了「给匿名块加 id」的正规做法,不必手改文档:

```
geml set f.geml '@b7e2f118' --head    # stdin: === note {#warn}
```

### 5.3 写完地址就变了

`set` 改了内容,该块的 `@` 地址随之改变。所以 `set` 成功且目标是 `@` 地址时,往 **stderr** 印一行新地址,脚本连改两次不必重新列出。

## 6. 列出:补全,一行一个**唯一**地址

今天 `listIds()` 只遍历 `doc.ids`,匿名块完全不在列表里 —— 而它们是能被操作的。补全后:

```
#top                 heading   h1    Top
#sect                heading   h2    Sect
#warn                note            L20-22
=== meta             meta      anon  L1-4
=== note@a3f9c1d2    note      anon  L5-7
=== note@b7e2f118    note      anon  L9-11
```

### 6.1 印哪个地址:最短的唯一地址

一个块可能有多个合法地址(§3.3:`@<hex>` 对带 id 的块也生效)。列出档印**最短的那个唯一地址**:

| 情况 | 印什么 |
|---|---|
| 有 `#id` | `#id` |
| 匿名,且 `=== type` 恰好唯一 | `=== meta` |
| 匿名,同类型有多个 | `=== note@a3f9c1d2` |
| 匿名,且与同类块逐字节相同 | `=== note@a3f9c1d2~1` |

`=== meta` 与 `=== note@…` 不是两套规则,是同一条规则在「类型唯一 / 不唯一」时的两种结果。

**类型筛 `=== note` 不出现在列表里。** 它是能打的选择符,但不是「一个单元的地址」—— 它匹配 3 个。列出档枚举的是单元的地址,一行一个。

### 6.2 两条不变式

1. **第一列恒可粘回 `get` 和 `set`,而且两边都恒定唯一。** 这是去掉类型筛行换来的:列表上再没有「只能读、不能写」的行,也就不需要一个 `×N` 列去标注它。
2. **一个块只占一行。** 与 §6.1 的「最短唯一地址」是同一件事的两面:一个块有多个地址,但列表只承诺给它一个。

(早先的草案里,类型筛作为「组地址」也占一行并带 `×N` 列。去掉了 —— 它与「一行一个地址」冲突,而它承载的信息在去掉之后不再需要:所有列出的地址都唯一。)

### 6.3 `anon` 列

**所有没有 `#id` 的块都标 `anon`**,包括 `=== meta` 那种靠类型唯一成立的。带 hash 的行地址本身已经说明它是匿名的,`=== meta` 那行不标就看不出来 —— 而「这个块还没有 `#id`」正是你可能想动手的信息(`set '=== meta' --head` 就能给它加,见 §5.2)。

### 6.4 靠唯一性成立的地址会因别处的编辑失效

`=== meta` 这类地址的唯一性来自「文档里只有一个 meta」。有人加了第二个 meta,它就不再唯一 —— `get '=== meta'` 开始返回两份内容,`set '=== meta'` 开始报 exit 2「匹配 2 个」。

**失效方式是响的,不会静默写错**,可以接受。`#id` 与 `@<hex>` 不受此影响:前者是主键,后者过期时匹配不上(§3.2)。

### 6.5 为什么 1 个时仍然是列表

选哪一档由**命令形式**决定,不由数据决定。若文档恰好只有一个可寻址单元时 `get f` 就吐内容,形状又回到看数据脸色 —— 那正是本轮要消灭的东西。列出档恒定输出列表,一行也是列表。

### 6.6 空文档

**exit 0,`--json` 印 `[]`**,text 模式 stderr 一行说明。这一档的提问是「把全部列给我」,空集是它的合法答案,不是查找失败;而且 `get f --json | jq length` 在纯散文文档上不该挂掉。

与「类型筛 0 个报 exit 1」不矛盾:那边是「你点名要 X,没有 X」,查找失败。`grep` 无匹配退 1 是同一条道理。

## 7. 一条规则:绝不静默丢弃调用方打出来的东西

本轮所有报错都是这一条的实例,不是四处各判一次:

| 情形 | 今天 | 定为 |
|---|---|---|
| 列出档带 `--head`/`--body` | 静默忽略 | **exit 2** |
| `--head` 与 `--body` 同给 | 静默让 head 赢(`set` 已报错) | **exit 2** |
| `--json` 与 `--head`/`--body` 同给 | 标题上生效、块上静默忽略 | **exit 2** |
| `=== code {lang=py}` | 静默忽略属性,返回全部 code | **exit 2**,见下 |

```
$ geml get f.geml '=== code {lang=py}'
error: only `#id` is supported as a filter key today (got `lang`) — use `=== code`
       for every code block, or address one by `#id` / `@<hex>`.        # exit 2
```

措辞是「**今天只实现了 `#id` 这一个 key**」,不是「花括号没有意义」。§2 已把属性 key 声明为设计的一部分;将来实现是**填满一个已声明的模型**,不是推翻「花括号无意义」再走回头路。

**本轮不实现属性过滤**:要给扫描层 `collectSpans` 加 attrs(`TypeMatch` 现为 `{span, id?}`),并定死一整套匹配语义(引号、类 `.warn` 算不算 key、多 key 是否 AND、值含空格)。`@<hex>` 已经覆盖「精确定位任意一个块」;属性过滤是另一个维度(按条件批量筛),等真实需求。

### 7.1 `--json` 为什么不能被 `get | --to json` 取代

实测:

```
get f '#n' --json           → {kind,type,mode,classes,attrs,id,children}   裸节点
get f '#n' | geml - --to json → {kind:"document",children,ids,diagnostics}  文档信封
```

管道那条把抽出来的块当成一篇新文档重新解析,多一层信封;标题那档差得更远 —— `get '#sect' --json` 的 `{kind:"section"}` 信封是 `get` 合成的,重新解析那段文本产生不出来。列出档的 `--json`(行数组)更是没有对应物,`geml_list` 直接依赖它。`--json` 是这个问题的结构化答案,不是顺手换格式。

`--json` 的返回:

| 选择符 | 返回 |
|---|---|
| 列出 | 行数组 |
| 精确档 · 块 | 模型节点 |
| 精确档 · 标题 | `{kind:"section", …, blocks:[…]}` |
| 类型筛 1 个 | 模型节点 |
| 类型筛 N 个 | **N 个模型节点的数组** |

最后一行是破坏性变更:今天是 `{kind:"blocks", type, matches:[{lines}]}`。全仓库只有一个消费方,是测试(`get-set.test.mjs:995`),无产品代码依赖。

| 0 | 取到了 / 写成功(列出空集也算) |
| 1 | 地址解析不到:id 不存在、标题不匹配、该类型一个都没有、`@<hex>` 不匹配(含已过期) |
| 2 | 用法错:§7 表中四种、`set` 遇 N 个匹配 |

## 9. 相对今天的改动

**破坏性(4 条)**

1. 类型筛匹配 N 个:坐标列表 exit 0 → **N 份内容**
2. 类型筛匹配 N 个 + `--json`:`{kind:"blocks"}` → **节点数组**
3. `--json` + `--head` 组合:(部分)生效 → **exit 2**
4. `=== type {非 #id 的 key}`:静默当类型筛 → **exit 2**

**新增 / 收严(7 条)**

5. `=== type@<hex>[~n]` 内容地址(`@<hex>` 亦可),`get` / `set` 均可用
6. `set` 接受完整选择符语法(今天只认 `#id`;给 `## Sect` 会报 ``no block with id `# Sect` ``)
7. `set` 遇 N 个匹配 → exit 2;成功写入 `@` 地址后 stderr 印新地址
8. `get` 补 `--body`
9. `--head`/`--body` 在类型筛档逐个作用(今天被静默丢弃)
10. `--head` 与 `--body` 同给 → exit 2
11. 列出补全:每个匿名块一行(最短唯一地址,§6.1)+ `anon` 标注;类型筛不再作为「候选列表」输出到 stdout

## 10. 非目标

- **属性 key 的实现**(§7)。已声明,未实现。
- **`delete` / `rename` / `revert` 共用这套语法。** `delete` 天然成立(它本就收多个 id,N 对它有定义),但本轮限定 `get` / `set`,扩展单独立项。
- **`@` 地址进入文档或引用**(§3.3)。硬约束,不留口子。
- **MCP `geml_get` 的 `part` 参数。** `geml_set` 有 `part: whole|head|body`,`geml_get` 没有;`get --body` 落地后两边应当对称,否则 MCP 层能写不能读同一个部位。记为连带项,不在本轮。

## 11. 顺带查到的既有缺陷(不在本轮)

`.gemlhistory` 的 key 文法要求 id 字母开头(`history.ts` 的 `KEY`),而 `attrs.ts:51` 对 `#` 后面写什么都收 —— 实测 `=== note {#2}` 完全合法、`check` 干净。也就是说**一个 id 为 `2` 的块,在 history 那层匹配不上 `#2` 这个 key,会掉进 `@sha8` 分支**。两层对 id 文法的认知不一致。与本轮无关,单独处理。
