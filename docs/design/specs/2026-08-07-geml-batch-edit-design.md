# GEML 批量编辑 —— 一次调用改多个块 — 任务说明

状态：**待评审**。由一次基准回放暴露出来的缺口，数据见下文第 2 节。
基线：`main` @ `4bf54bb`（`list`/`find` 两个发现动词已落地，目录链接修复已合入）。
前置阅读：`2026-08-04-geml-get-set-selector-design-change.md`（选择符、`--head`/`--body` 的定义与基数规则）· `docs/benchmarks/addressing-cost_CN.md`（寻址成本基准）。

## 1. 出发点：agent 会批量改，而 GEML 一次只能改一块

这不是要让 GEML 取代 `sed`。**按场景选工具本来就是对的**——已知确切旧串的机械替换，用原命令又快又省；需要看到内容、需要稳定寻址的改动，才轮到 GEML。这份说明只针对**后者里被批量拖累的那部分**。

今天 `geml set` 的形状是一次一块：

```sh
geml set doc.geml '#a' --in - < a.txt
geml set doc.geml '#b' --in - < b.txt
geml set doc.geml '#c' --in - < c.txt
```

三次进程启动、三次解析、三次写盘，而且**三次之间文档是"改了一半"的状态**——中途失败就停在那里。

## 2. 数据：批量是真实 agent 的主要工作方式之一

把一个 agent 编辑 `README_CN.md` 一整天的会话记录逐条恢复出来，共 33 处修改，其中 14 处可以回放对照。按**做法**拆开：

| 编辑方式 | n | 读进来的字节 | 说清楚改哪里 |
|---|---:|---:|---:|
| 一次一处（`Edit`） | 4 | GEML 省 **2.60×** | GEML 省 **73.8×** |
| **一条脚本批量替换** | **10** | **GEML 贵 1.3×**（0.77×） | GEML 省 4.5× |

**10 / 14** 的修改是批量做的。批量之所以便宜，是因为它**一次定位分摊给多处修改**，并且**不读内容**——旧串已知，直接盲替换。GEML 目前两样都做不到：每处都要 `find` + `get`，每处一次 `set`。

结论不是"GEML 输了"，而是：**GEML 在它擅长的那类修改上赢得很多（2.6× / 73.8×），但缺一个批量入口，导致它在不擅长的场合被迫逐块付费。**

## 3. 设计

### 3.1 一个补丁，一次事务

新增 `geml patch`（暂名，见 §5 待定）：

```sh
geml patch doc.geml --in patch.geml
geml patch doc.geml --in -            # stdin
```

补丁文件本身就是 GEML——**不引入第二套语法**，这是本设计最重要的约束。每个块的 `#id`（或任何选择符）指明目标，块的内容就是新内容：

```geml
=== patch {target="#intro"}
新的开场段落。
===

=== patch {target="#tbl" part=body}
| 列 | 值 |
| :- | :- |
| a  | 1  |
===
```

- `target=` 接受 `set` 今天接受的**全部选择符**（`#id`、`## 标题`、`=== type`、`@hex`、`L27-58`）。
- `part=` 对应 `set` 的 `--head|--intro|--body`，缺省 `whole`。
- 目标必须**恰好命中一个块**，与 `set` 的基数规则一致；命中零个或多个都是错误。

### 3.2 要么全成，要么全不动

这是批量最该带来的东西，也是逐块 `set` 给不了的：

1. 解析补丁，解析目标文档。
2. **先全部解析、全部定位**——任何一条 `target=` 命中零个或多个，立即失败，**文档一个字节都不动**。
3. 全部拼接完成后**整体重新解析一次**；只要产生 error 级诊断，就整体放弃。
4. 通过之后一次写盘（临时文件 + rename，与 `skill install` 同样的原子写）。

失败时的报错要指名道姓：哪一条 `target=` 出的问题、是没命中还是命中多个。

### 3.3 与 `.gemlhistory` 的关系

一次 `patch` 是**一次修订**，不是 N 次。这与它作为事务的语义一致，也让 `revert` 能整体回滚一批相关修改——这恰恰是逐块 `set` 做不到、而批量脚本更做不到的事。

## 4. 不做什么

- **不做正则/字符串替换。** 那是 `sed` 的活，做得比我们好。GEML 的批量是**按地址**批量，不是按模式批量。
- **不做跨文档批量。** 一次 `patch` 只作用于一个文档；跨文档是调用方的循环。
- **不引入新语法。** 补丁是 GEML 文档，用 `=== patch` 块承载，能被 `geml check` 校验。

## 5. 待定 —— 分支 `feat/geml-patch` 已按下面的取舍实现，供评审推翻

1. **动词名。** `patch` 还是 `set --batch`？前者更直白，后者不新增顶层动词。倾向 `patch`——它的语义（事务、多目标、一次修订）和 `set` 差别足够大。
2. **块类型名。** `=== patch` 需要进类型注册表（规范 §3/§8），还是用 `=== text {target=…}` 这种已有类型加属性？前者更清楚，代价是规范新增一个类型。
3. **删除与插入。** 补丁里要不要支持"删除这个块"和"在此之前/之后插入"（对应 `delete` / `add`）？先做替换，删除和插入留待有真实需求再说——**多用减法**。

## 6. 验收

- 一条补丁改 N 个块：一次进程、一次写盘、`.gemlhistory` 里一次修订。
- 任一 `target=` 命中零个或多个 → 退出非零，**文档未被修改**（测试要断言文件字节未变）。
- 拼接后文档产生 error 级诊断 → 整体放弃，**文档未被修改**。
- 跨平台：CRLF 文档补丁后仍是 CRLF；路径与换行在 Windows 与 Linux 上行为一致。
- 基准回放（`docs/benchmarks/`）里"批量"那一档重测，确认 0.77× 转正。

### 5.x 实现取舍（`feat/geml-patch`）

| 待定项 | 取的做法 | 理由 / 代价 |
|---|---|---|
| **1. 动词名** | `patch` | 事务、多目标、一次修订，与 `set` 差别足够大。代价：多一个顶层动词 |
| **2. 块类型名** | 注册 `=== patch`（raw 正文），并把 `target` / `part` 加进已知属性表 | §4 要求补丁能被 `geml check` 校验；不注册就会带 3 条 `unknown attribute` 警告。**代价：规范新增一个类型，可能需要 GEP**——这是最需要评审拍板的一条 |
| **3. 删除与插入** | 只做替换 | 按设计的「多用减法」。删除仍走 `delete`，插入仍走 `add` |

### 5.y 实现中新增的一条规则：重叠即拒绝

设计里没写、但实现必须回答：两条指令的目标区域**互相包含**时怎么办（例如 `target="#intro" part=intro` 与它区域内的 `target="#n"`）。

结论是**拒绝，一个字节不动**。谁覆盖谁取决于施加顺序，而补丁文件对顺序不作任何承诺——静默地按某个顺序执行，等于让结果依赖一个没人声明过的东西。报错点名两条指令各自在补丁里的行号。

### 5.z 与 `--intro` 的行为必须逐字节一致

`part=intro` 走的是和 `set --intro` 同一套空行补齐规则（缺了才补）。测试直接断言两条路径产出**完全相同的字节**——一个语义两种行为，比没有这个功能更糟。
